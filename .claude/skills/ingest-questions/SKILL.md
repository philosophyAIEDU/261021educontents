# /ingest-questions — 학생 질문 정제·분류·업로드

작업 폴더: 이 프로젝트 폴더. **규칙 2가 최우선이다: 학생 이름·학번·연락처·성적·프로필 정보는 어떤 형태로도 저장하지 않는다.** 학생 질문은 "학생들이 어디서 막히는가"를 알려 주는 귀한 자산이지만, 쓰는 것은 **패턴**이지 원문이 아니다 (규칙 4).

## 0. 입력
- `raw/questions/`의 파일(txt/csv/xlsx를 csv로 저장한 것/json 등)을 읽는다. 폴더가 없으면 만든다. `raw/`는 git에 올라가지 않는다.
- 질문이 **어느 자료에 대한 것인지**(`processed/`의 id, 예: `lecture-01`)를 확인한다. 파일 이름이나 내용에 없으면 묻는다. 한 과목 전체에 대한 질문이면 가장 가까운 자료 id를 고르게 하거나, 과목의 첫 자료 id를 쓰고 `course`에 과목을 적는다.
- 교수님 본인의 수업·자료에 대한 질문만 다룬다. 다른 교수의 수업 질문이면 멈추고 확인한다 (규칙 3).
- **성적표, 출석부, 점수가 붙은 강의평가 원자료, 상담 기록은 받지 않는다.** 받았으면 이유를 설명하고 질문·의견 텍스트만 따로 저장해 달라고 한다.
- 학교의 개인정보·강의평가 활용 지침이 있으면 그것이 우선이라고 처음 한 번 알린다.

## 1. 신원 정보 제거 (저장 전에 반드시)
- 지운다: 이름, 학번, 아이디, 이메일, 전화번호, 프로필 링크·이미지, 학과+학년·분반·조 번호 조합, 성적·점수, 작성자 관련 컬럼 전체.
- 본문 속 개인정보도 지우거나 `[삭제]`로 가린다: 다른 학생 이름("○○이가 말한 것처럼"), `@멘션`, 개인 사정(건강·가정·경제 사정), 특정인을 알아볼 수 있는 경험담의 세부.
- 교수님·조교의 답변은 질문으로 취급하지 않고 제외한다. (답변 내용이 지식이면 교수님 자료로 따로 `/ingest`한다)
- 위 처리 후 남은 텍스트에서 다시 한 번 `@`, 이메일, 전화번호, 학번 패턴을 검사한다. 남아 있으면 업로드하지 않는다.

## 2. 질문 유형 분류
질문 하나에 하나의 유형만 붙인다 (`question_type`). 애매한 것은 추측하지 말고 모아서 묻는다.
- `개념 질문`: 무엇인지, 왜 그런지, 두 개념의 차이를 묻는다
- `적용 질문`: 실제 상황·과제·연구에 어떻게 쓰는지 묻는다
- `오개념`: 질문이나 의견 속에 잘못 이해한 내용이 드러난다 (가장 귀한 자료다. 무엇을 어떻게 오해했는지 `misconception`에 한 줄로 적는다)
- `요청`: 다음에 다뤄 달라, 자료·예시를 더 달라
- `긍정 피드백`: 도움이 됐다, 이해가 됐다
- `개선 피드백`: 어렵다, 빠르다, 불편하다
- `기타`: 수업과 무관, 행정 문의(시험 범위·출결 등) — 업로드하지 않는다

## 3. 태깅과 표
각 질문 문서의 필수 태그 6개를 채운다 (`CLAUDE.md`).
- `format`: `학생 질문`, `category`·`target_audience`: 부모 자료와 같게
- `knowledge_type`: 질문이 겨냥한 지식의 유형 (개념 질문 → 보통 `개념·이론`, 적용 질문 → `방법·절차`)
- `created_at`: 질문 날짜가 있으면 그 날짜, 없으면 `null`
- `key_message`: 질문을 **교수님이 다시 쓴 한 문장 요약**으로 (원문 말투를 옮기지 않는다, 개인정보 없이)
- 추가 필드: `question_type`, `misconception`(오개념일 때만), `related_concept`(`knowledge-map.md` 1절 개념이 있으면), `parent_id`(부모 자료 id), `body`(정제된 질문 본문)
- 결과는 **표로 먼저 보여준다** (id, 질문 유형, 요약, 관련 개념, 삭제한 정보 종류와 건수). 사용자가 확인하기 전에는 저장하지 않는다.
- 날짜가 없는 질문이 많으면 그 상태로 올릴지 묻는다. 기본은 업로드 보류이며, 허용할 때만 `--allow-missing created_at`.

## 4. 저장·업로드
1. `processed/qna-<부모id>-NN.json`으로 저장한다 (질문 1개 = 문서 1개, `id`는 `qna-<부모id>-NN`).
2. `node scripts/upload.mjs --id <id>`로 dry-run 검증한다 (신원 관련 필드, 이메일·전화번호·학번·`@아이디`·성적 표현이 있으면 거부된다). 여러 건이면 id를 하나씩 반복한다.
3. **검수 에이전트 호출 (필수)**: `--commit` 전에 반드시 `data-checker` 에이전트(Agent 도구, `subagent_type: "data-checker"`)를 호출한다. 프롬프트에 이번에 올릴 질문 문서 id 전체와 "학생 질문 문서이므로 신원 정보를 특히 엄격하게 볼 것"을 적는다.
   - `판정: 업로드 중단`이면 **질문은 한 건도 올리지 않는다.** 문제가 된 문서와 이유를 한글로 전하고, 해당 질문을 다시 정제하거나 제외한 뒤 검수를 다시 돌린다. 이 검수는 사용자가 요청해도 건너뛰지 않는다 (규칙 2).
   - "확인 필요" 항목(호칭, 자기소개, 개인 사정 등)은 사용자에게 보여주고 답을 받는다.
4. 검수를 통과하고 사용자가 확인하면 `node --env-file=.env scripts/upload.mjs --id <id> --commit`. 대상은 Firestore `knowledge_input`이다. 키 파일(`keys/`)의 내용은 읽지 않는다. 경로는 `.env`에 있다.

## 5. 기록과 다음 단계
- `reports/ingest-log.md` 맨 아래에 추가한다: 날짜, 부모 id, 질문 수, 유형별 건수, 오개념 주제 목록(원문 없이), 제외 건수(기타·답변), 신원 정보 제거 건수, 검수 결과, 업로드 결과. **기록에도 학생 정보를 쓰지 않는다.**
- 끝나면 "지식 지도 5절(자주 묻는 것·자주 틀리는 것)에 반영할까요?"를 묻고, 동의하면 `/knowledge-map` 갱신 모드로 5절만 고친다. 오개념이 3건 이상이면 `/draft 학습자료 <개념> 오개념 바로잡기`나 `/draft 평가문항`을 제안한다.

## 금지
- 학생 신원 정보를 `processed/`, Firestore, 리포트, 채팅 요약 어디에도 남기지 않는다.
- `raw/questions/` 원본을 수정하거나 커밋하지 않는다.
- 사용자 확인 없이 `--commit` 하지 않는다.
